# Runtime V4 Architecture Audit

## 1. How the existing 259 candidates were generated

The frozen 259-film universe in `mvp/artifacts/recommendation_runs/20261003T075635Z` was produced by `mvp/src/candidates.py` using live TMDB discovery strategies:

- `/movie/popular`
- `/movie/top_rated`
- `/discover/movie` for recent releases
- `/discover/movie` for genre-diverse sampling
- `/movie/{id}/recommendations` seeded from a handful of watched films

The pool was deduplicated, watched-film exclusions were applied, then each candidate was enriched with TMDB details and cached embeddings before B3 scoring.

## 2. Which TMDB APIs/endpoints are currently used

The repository uses the following TMDB endpoints:

- `GET /search/movie`
- `GET /movie/{movie_id}`
- `GET /movie/popular`
- `GET /movie/top_rated`
- `GET /discover/movie`
- `GET /movie/{movie_id}/recommendations`

These are implemented across `mvp/src/prepare.py` and `mvp/src/candidates.py`.

Reusable functions and modules:

- `mvp/src/prepare.py`

- `mvp/src/mvp_deployment.py`
  - `build_film_document`

  - `build_taste_profile`

These utilities remain useful because they are grounded in the frozen model assets and the current TMDB ingestion path.

## 4. How candidate film documents are constructed

The current canonical film document is built in `mvp/src/mvp_deployment.py` and includes:

- title
- release year
- TMDB genres
- original language
- production countries
- overview

This is versioned as `film_doc_v1`. It is adequate for the frozen B3 cache, but runtime_v4 needs a separate `film_doc_v2` so request relevance, qualification, and explanation are explicitly grounded in the request-aware catalog stage.

## 5. How `text-embedding-3-small` embeddings are generated/cached

Candidate document embeddings are generated through `load_or_generate_candidate_embeddings(...)` in `mvp/src/mvp_deployment.py` using `text-embedding-3-small` and cached in:

- `mvp/artifacts/models/b3_mvp/candidate_embedding_cache/candidate_embeddings.csv`

The same cache format is reused elsewhere when candidate documents have the same text representation.

## 6. How the frozen PCA transform is loaded

The frozen PCA object is stored in:

- `mvp/artifacts/models/b3_mvp/pca.joblib`

It is loaded through `mvp/src/mvp_deployment.load_model_bundle(...)`, which returns the PCA object alongside the frozen ridge bundle and metadata preprocessor.

## 7. How the frozen Ridge/B3 model is loaded

The frozen ridge model is stored in:

- `mvp/artifacts/models/b3_mvp/model.joblib`

It is loaded through `mvp/src/mvp_deployment.load_model_bundle(...)`. The saved bundle contains:

- the ridge regressor
- the fitted `StandardScaler`
- the selected PCA dimensionality
- the trained metadata feature builder
- the feature column list

## 8. Exact B3 feature schema

The frozen metadata feature builder is `ConventionalMetadataFeatureBuilder` in `mvp/src/models.py`.

Feature families:

- `release_year_z`
- one-hot genres from `tmdb_genres`
- one-hot languages from `tmdb_original_language`
- one-hot countries from `tmdb_production_countries`
- one-hot decades from `release_decade`

These are concatenated with the latent PCA components:

- `latent_pca_001` ... `latent_pca_###`

The final ridge feature matrix is the metadata block plus the latent PCA block.

## 9. How the 62-dimensional semantic vectors are generated/cached

The frozen 62-dimension taxonomy is defined in `mvp/src/semantics.py` as `SEMANTIC_COLUMNS`.

Semantic vectors are generated by `mvp/src/prepare.classify_semantic_vectors(...)` and cached in:

- `mvp/artifacts/semantic_vectors/semantic_vectors.csv`

The same taxonomy is used by the taste-profile builder and by the generative validators.

## 10. Current LangChain architecture

The current orchestration lives in `mvp/src/generative/recommendation_chain.py`.

It performs:

- intent parsing
- candidate-context construction
- hard filtering
- contextual retrieval for `runtime_v3`
- LLM generation
- validation
- repair
- fallback

That architecture is still useful as a reference, but runtime_v4 should not simply wrap it.

## 11. Current LangSmith tracing/evaluation architecture

Tracing is implemented through `langsmith.run_helpers.trace(...)` in the generative chain.

Evaluation lives in:

- `mvp/src/generative/langsmith_evaluation.py`
- `evaluation/langsmith/evaluators.py`

The existing evaluation contract focuses on:

- candidate compliance
- identity integrity
- hard constraints
- taste-signal grounding
- Goodreads separation
- sensitive inference guardrails

## 12. Current validator behavior

Validators currently live in `mvp/src/generative/validators.py`.

They enforce:

- candidate existence in the supplied context
- hard constraints
- duplicate rejection
- taste-signal grounding against the candidate semantic evidence
- Goodreads as non-ranking evidence
- no-match / clarification states

This is a strong base, but runtime_v4 needs stricter request-grounding and qualification-aware validation.

## 13. Components to reuse versus replace

Reuse:

- TMDB client utilities
- watched-film exclusion logic
- frozen B3 model bundle
- frozen PCA
- frozen 62-d taxonomy
- semantic vector cache machinery
- taste-profile construction
- LangSmith tracing patterns

Replace:

- the static candidate universe as the runtime candidate source
- the single-stage request-to-explanation flow
- the request-matching contract
- the selection contract
- the validation contract
- the runtime evaluation dataset

Runtime_v4 should treat request relevance, historical preference, semantic evidence, and explanation as separate layers.
